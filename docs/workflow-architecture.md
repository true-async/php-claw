# Архитектура Workflow

Дизайн-документ: модель «умных workflow» для php-claw — идея, как устроен код
**сегодня**, и что ещё впереди. По тексту помечено, что **реализовано**, а что **в
планах**. Это спека, а не туториал.

## Идея

Агент решает каждую задачу заново, и его опыт исчезает вместе с окном контекста.
Workflow лечит это, превращая модель из **интерпретатора** в **компилятор плюс
оркестратор**: человек описывает процесс словами, агент собирает из готовых блоков
исполняемый PHP-класс, и дальше этот класс прогоняется как код. Структура процесса
детерминирована и восстановима, а отдельные шаги внутри могут быть агентными (вызовы
LLM) там, где нужна гибкость.

Отличие от «скилов»: скил перечитывается и толкуется моделью при каждом запуске
(дорого, недетерминированно). Workflow пишется один раз, исполняется предсказуемо, его
можно прочитать, проверить, сохранить и переиспользовать.

## Что такое Workflow (текущая модель)

**Workflow — это PHP-класс с состоянием в собственных полях.** Шаги — это **методы**,
помеченные атрибутом `#[Step]`. Базовый `WorkflowAbstract` — **тонкий хелпер, а не
движок**: он ничего «за шаг» не исполняет, он лишь делает тело шага короче и durable.

```php
interface WorkflowInterface
{
    public function name(): string;
    public function run(): void;   // точка входа; результат — состояние, что осело в полях
}
```

- **Состояние** — поля класса: **только восстановимое рабочее состояние для durable resume**
  (снапшот `{state, done}`), НЕ канал передачи данных между шагами. Что должно дойти до
  следующего шага или до критика — кладётся в **artifact** (глобальный) или **handoff**
  (следующему шагу). Это два и только два канала вывода — см. «Контекст между шагами».
- **Шаг** — метод с `#[Step]`, объявленный **`protected`** (валидатор отклоняет `public`/
  `private`: шаг гонит база, наружу он не торчит). Тело пишет автор (человек или AI) руками:
  собрать промт, позвать `ai()`, позвать `tool()`, записать результат в поле.
- **`run()`** — просто точка входа. По умолчанию база гонит `#[Step]`-методы в порядке
  объявления; автор может **переопределить** `run()` и оркестрировать руками обычным
  PHP (`if`/`while`, под-workflow).

Пример — `src/Workflow/Example/ReviewFileWorkflow.php`:

```php
final class ReviewFileWorkflow extends WorkflowAbstract
{
    public function name(): string { return 'review-file'; }

    #[Step]
    protected function read(): void
    {
        // вывод шага — в artifact (глобальный канал), не в поле
        $source = $this->tool('read_file', ['path' => (string) $this->param('path')]);
        $this->artifact('source', $source);
    }

    #[Step]
    protected function findIssues(): void
    {
        // следующий шаг читает предыдущий из журнала, а не из поля
        $source = $this->tool('recall', ['what' => 'artifacts', 'name' => 'source']);
        $this->artifact('issues', $this->ai("List the problems in this file:\n\n" . $source));
    }

    #[Step(critic: 'strong')]
    protected function propose(): void
    {
        $issues = $this->tool('recall', ['what' => 'artifacts', 'name' => 'issues']);
        // критик ('strong') судит ЭТОТ артефакт; слабое предложение он завернёт, шаг переделается
        $this->artifact('proposal', $this->ai("Propose concrete fixes for:\n\n" . $issues));
    }

    protected function criticRules(): array
    {
        return ['strong' => 'Reject the proposal if it is vague or does not give concrete, applyable fixes.'];
    }
}
```

Заметь: ни одного `$this->field = $this->ai(...)`. Каждый шаг кладёт результат в **artifact**,
следующий поднимает его через `recall`, а критик судит артефакт — это и есть две-канальная модель.

## Параметры (в этом и есть супер-сила)

Workflow **параметризирован**: принимает входные параметры и потому описывает не одну
задачу, а целый их класс. Workflow «прочитай и отревьюь файл» бесполезен без ответа
«какой файл» — и это **параметр**. Один и тот же класс работает для любого файла:
достаточно передать параметр при запуске. Связка **Workflow + параметры** и есть его
мощь: класс — это шаблон процесса, параметры — конкретика.

Заполнять параметры может **человек или агент**: «отревьюь src/Foo.php» агент
превращает в `path = src/Foo.php`. Технически шаг читает их через `$this->param('path')`;
параметры приходят в конструктор инстанса.

## База-хелпер: поверхность `WorkflowAbstract`

Это и есть «единственная дверь» — генерируемый подкласс трогает мир только через эти
методы:

- **`ai(string $prompt, ?array $tools = null, ?string $agent = null): string`** — один обмен
  с моделью; турн-луп внутри (ReAct: round-trip'ы с инструментами) — внутренняя деталь.
  **`$tools` по умолчанию `null` = ВСЕ инструменты прогона** — способному агенту дают полную
  палитру, это норма. Сужение — исключение: список = только эти, `[]` = вообще без тулов
  (для шага-судьи или вызова, который должен лишь вернуть текст/код). Доступные тулы ещё и
  **именуются в системном промпте** (briefing), чтобы модель надёжно тянулась к нужному
  (`recall`/`done`/…), а не «замечала» их через раз. `$agent` — имя роли с моделью этой роли:
  worker (дешёвый дефолт) / **worker-smart** (сильнее) / reviewer / supervisor /
  **supervisor-smart** / planner; неизвестная роль — мягкий откат на модель scope.
- **`tool(string $name, array $params): string`** — один вызов инструмента через executor
  прогона. **Ошибка тула НЕ бросает** — возвращается строкой `tool '<name>' failed: …`
  (как и ошибка тула внутри `ai()` отдаётся модели, а не роняет ход): шаг может её увидеть и
  починиться, а не падать.
- **`artifact(string $label, ?string $text = null, ?string $file = null): void`** — записать
  именованный выход шага (текст или файл, что шаг создал). Артефакты пишутся в **журнал**
  (видны в `claw log`) и передаются **критику** шага. Хранятся по шагам на весь прогон.
- **`param(string $name): mixed`** — вход прогона.
- **`ask(string $question): string`** — спросить того, кто стоит в `EnvKey::Ask`: консоль
  (человек, приглашение `Request>`) или цепочку `EscalatingSpeaker` (супервизор-агент → человек).
  Нет канала — осмысленная ошибка.
- **`critique(): ?string`** — внутри шага с критиком: последняя подсказка критика/супервизора
  (`null` на первом проходе), чтобы переделка её учла.
- **`criticRules(): array` / `criticRole(): string`** — переопределяемые хуки: правила каждого
  критика (имя → текст критериев) и постоянная роль ревьюера (см. «Критик» ниже).
- **`step(string $name): void`** — выполнить `#[Step]`-метод, если он ещё не сделан, прогнать
  его критика (если объявлен, ниже) и снять снапшот состояния. По умолчанию `run()` зовёт его
  на каждый шаг; в своём `run()` автор зовёт его в нужном порядке/по условию.
- **`find()/set(EnvKey|string)`** — читать/локально переопределить окружение прогона
  (обычно из `init()`).
- **`log(action, message, context)`** — записать в журнал событие уровня задачи.
- **`init()`** — хук: настроить scope прогона до первого шага.

Локальные тулы прогона (в палитре каждого `ai()`): **`recall(what, name?)`** — поднять из
журнала контекст этого прогона (`task` — бриф задачи; `workflow` — карта шагов; `step`/`tool`/
`artifacts` — история шага/тула/артефакты); **`done(summary)`** — объявить задачу решённой и
завершить workflow досрочно, пропустив оставшиеся шаги. Шаг может дать себе и **свой**
бесшовный тул, пометив метод `#[\Claw\Workflow\Tool(description: …)]` — он становится тулом,
видимым в `ai()` этого workflow (типы параметров → схема); удобно для самопроверки (свой
`validate()` гоняет `php -l`/тесты, и модель чинит себя в том же обмене).

## Состояние и durable resume (снапшот)

Прогон **durable по СНАПШОТУ** (не по replay результатов):

- после каждого шага база сохраняет в `WorkflowStateStore` пару `{state, done}` по
  `runId` — где `state` это поля воркфлоу, а `done` это имена выполненных шагов;
- в конструкторе снапшот загружается: `state` **восстанавливается на поля** (рефлексией
  по собственным свойствам подкласса), `done` — в список сделанных;
- `step(name)` **пропускает** шаг, уже попавший в `done`. Поэтому пропущенный шаг
  ничего не теряет — его эффект уже в восстановленном состоянии.

**Реализовано:** `SqliteStateStore` — боевой стор: снапшот `{state, done}` в БД проекта
(`INSERT OR REPLACE` по `runId`) + монотонный `state_seq` для leaf-id; переживает рестарт.
`InMemoryStateStore` остаётся для тестов. Реестр прогонов — `ProjectStore` (ledger `runs`);
`resumableRun()` находит прерванный прогон (статус всё ещё `running`), и `claw run`
переиспользует его id — солвер восстанавливает сохранённое состояние и до-исполняет только
незавершённый хвост.

**Граница durability:** снапшот снимается на ГРАНИЦЕ ШАГА. Длинный шаг (внутренний
ReAct-луп `ai()`) внутри не чекпоинтится — краш посреди шага повторит шаг целиком.

**Handoff тоже durable.** Эстафета между шагами (см. «Контекст между шагами») живёт не только
в памяти: как только handoff сформирован, он пишется в стор **с привязкой к шагу-источнику**
(`saveHandoff(runId, fromStep, handoff)`). При resume в новом процессе конструктор поднимает
его (`loadHandoff`) и подставляет следующему шагу — модель **повторно не спрашивается** (turn-loop
история, из которой он формировался, уже недоступна). Сохранённый handoff от более раннего
перехода (его читатель-шаг уже отработал) считается **устаревшим и игнорируется** — следующий
шаг получает пустой контекст, как если бы краш случился мгновением раньше.

Контракт стора: `save(runId, state, done)` / `load(runId) -> {state, done}` /
`saveHandoff(runId, fromStep, handoff)` / `loadHandoff(runId) -> {from, handoff}` /
`nextId()` (монотонный id для leaf-вызовов — стор владеет идентичностью, воркфлоу id не
выдумывает). `SqliteStateStore` держит handoff в своей таблице `workflow_handoff` (одна строка
на прогон), отдельно от снапшота — пишется в другой момент.

## Environment (окружение прогона)

`Environment` — scoped `key→value` с ссылкой на родителя. `find()` ищет в этом scope,
затем поднимается к родителю — так цепочка **project → issue → workflow →
под-workflow** наследует значения, а ребёнок переопределяет только нужное. `EnvKey` —
каталог известных ключей: `Worker`, `Registry`, `ModelId`, `SystemPrompt`, `MaxHistory`,
`Store`, `Tracer`, `Agents` (роль→модель), `Ask` (канал к человеку/над-агенту), `Budget`
(тотальный лимит токенов+времени) + `TurnTokenLimit`/`TurnTimeLimit` (на один обмен) +
`BudgetPolicy` (`stop`|`ask`). Типобезопасные finders над «mixed»-мешком; `executor()`
собирается из реестра текущего scope.

## Инструменты и палитра (по умолчанию — все)

`Registry` — каталог инструментов. **По умолчанию `ai($prompt)` показывает модели ВЕСЬ реестр
прогона** (плюс локальные `#[Tool]`-методы этого workflow) — способный агент тянется к чему
нужно. Сужение — осознанное исключение: `ai($prompt, ['read_file'])` создаёт дочерний scope с
`registry.only(['read_file'])`, `ai($prompt, [])` — без тулов. Из реестра scope берутся **и**
спеки (что видит модель), **и** резолв исполнения (`executor()` бьёт по реестру scope) — то
есть инструмент **вне палитры** не рекламируется и не запускается. Сверх API-списка тулов их
имена+описания подставляются в **системный промпт** (briefing), чтобы модель надёжно их видела.

Исполнение идёт через `ChainExecutor` с middleware (audit / permission / timeout).
**Сейчас** executor воркфлоу собран без permission-middleware (автономный прогон =
фактически allow-all); реальная `Policy` (денлист, позже — AI-оценка риска) приедет с
run-path (ниже).

## Критик и супервизор

**Критик — декларативный аспект шага.** Шаг помечают `#[Step(critic: '<имя>')]`, и драйвер
`step()` сам, после метода, судит **то, что шаг положил в свои каналы вывода — artifact(ы) и/или
handoff** (НЕ возвращаемое значение: возврат шага движком игнорируется, см. «Контекст между
шагами»). Вердикт по идиоме `?string` (`null` = одобрено, строка = замечания). Шаг с критиком,
не оставивший ни артефакта, ни handoff'а, ничего не произвёл — критик это и фиксирует как
ошибку (а не «нет артефактов» как придирку). Имя критика — лишь ключ: **реальные правила** лежат
в переопределяемом `criticRules()` (`['<имя>' => '<текст критериев>']`); имя без правил роняет
прогон (это баг генерации, не молчим). Критик навешивается **конфигом**, применяет его машинерия.

**Промпт шага и промпт критика — одно целое, без противоречий.** Критерии критика обязаны
проверять ровно то, что шаг по своему промпту должен был произвести, в тех же терминах. Если
шаг просят «положи результат в artifact X», критик судит artifact X — а не требует того, чего
шаг по заданию не делал (классическая течь: критик, заточенный под «исполнить работу», судит
шаг-**генератор кода** и требует от него запуска тестов/артефактов исполнения — это требование,
которое шаг физически выполнить не может, и петля не сходится). Генератор обязан писать пару
«шаг ↔ критик» согласованной.

**Критик — это обычный AI со ВСЕМИ тулами**, а не текстовый судья: он открывает файлы-артефакты,
сам гоняет `php -l`/тесты и реально **верифицирует** (уверенная отписка над битым файлом будет
поймана). Его постоянная роль — переопределяемый `criticRole()` (по умолчанию «ты ревьюер:
проверь и верни замечания, не делай и не правь работу сам»).

**Критик судит, супервизор решает (proposer/disposer).** Критик недоволен → драйвер спрашивает
**супервизора** — это `ask`-канал, за которым `EscalatingSpeaker`: супервизор-агент отвечает
первым, не справился (`reply()` вернул `null` = «передай выше») → доходит до человека. Супервизор
решает ход: **направить** (его guidance кладётся в `$this->critique()`, шаг переделывается, критик
судит заново), **принять как есть**, или **стоп**.

**Мягкий предел петли — МАЛЕНЬКИЙ.** Счётчик раундов переделки: дефолт **2**,
переопределяемый на шаг через `#[Step(critic: '…', maxRounds: N)]`. Смысл критика — поймать и
дать переделать **один-два** раза, а не крутить десятки раундов: если за 1–2 захода замечания не
закрыты, дело не в «ещё разок», а в рассогласовании (промпт шага vs критик, или задача реально
требует человека) — поэтому на пределе **эскалация**: спросить супервизора «принять / ещё раз /
стоп»; спросить некого (автономно) → стоп, чтобы не жечь токены вечно. Поднимают кап точечно
только там, где переделка ЗАКОННО долгая (например, гейт на прогоне тестов). Аналогично у самого
turn-loop'а `ai()` есть мягкий кап на turn'ы. **Бюджет** (токены+время) — жёсткий backstop сверху.

**Канал `ask` и `EscalatingSpeaker`.** `EnvKey::Ask` несёт `SpeakerInterface` (`name(): SpeakerRole`,
`reply(string): ?string`, `null` = «передай выше»). Драйверы: `ConsoleSpeaker` (человек, `Request>`),
`AgentSpeaker` (агент гоняет свой turn-loop), `EscalatingSpeaker` (цепочка `[агент, …, человек]`).
Тот же канал интерактивит и `DefaultTurnLoop`: модель может посреди хода завершить ответ маркером
`[question] …` — луп зовёт `ask`, инжектит ответ как user-turn и продолжает (контекст непрерывен).

**Роли агентов и тиры.** Шаг направляет вызов именованной роли (`$this->ai($p, null, agent: 'reviewer')`):
канон — worker (дешёвый дефолт) / reviewer / supervisor / planner. Плюс **тиры**: `*_SMART`-роль
(`worker-smart`, `supervisor-smart`) — сильнее модель для тяжёлого мышления (генерация workflow,
ревью). Роли отличаются только моделью (`CLAW_AGENT_<ROLE>` → `Config::$agents` → `EnvKey::Agents`;
имя env `CLAW_AGENT_WORKER_SMART` читается как роль `worker-smart`, `_`→`-`).

**Супервизор-починка кода (`SuperviseWorkflow`).** Отдельная рунг лестницы: на runtime-**краше**
солвера run-path отдаёт (ошибка + код) роли `supervisor`, та пишет исправленную версию под НОВЫМ
именем класса (PHP не перечитывает уже загруженный класс), сохраняет через `define_workflow`, и
прогон **резюмируется** тем же `runId` — снапшот пропускает готовые шаги, переисполняет хвост.
Ограничено `MAX_REPAIRS`. Это про «**код** солвера упал»; «**работа** плоха» — это критик+супервизор
выше.

## Контекст между шагами: явные каналы (artifact / handoff / param)

> **Базовый принцип (важно — соблюдать строго).** Шаг передаёт что-либо дальше только через
> ЯВНЫЕ каналы — **artifact**, **handoff** или **param** — каждый под свою задачу.
> **Возвращаемое значение шага и «сохранить результат `ai()` в поле/переменную» — это НЕ канал.**
> Старая модель (`$this->source = $this->ai(...)`, `return $this->code` как полезная нагрузка)
> **отменена**: возврат шага движком игнорируется, поля класса — это только восстановимое
> рабочее состояние для resume (см. снапшот), а не способ передачи данных между шагами.

Три канала по назначению: **artifact** = контент (для модели/критика), **handoff** = прозовое
резюме (для модели следующего шага), **param** = чёткое значение (для КОДА следующих шагов). Первые
два — про вывод/работу шага; третий — про детерминированную передачу конкретной величины.

Каждый `ai()` стартует **со свежим контекстом** — он НЕ видит прошлые шаги, и движок сам ничего
между шагами не тащит (иначе контекст пухнет и «гниёт»). Поэтому то, что должно дожить до
следующего шага или до критика, шаг обязан **явно** положить в один из каналов:

- **Artifact — глобальный канал.** `$this->artifact(label, text|file)` фиксирует именованный
  выход шага. Артефакт **виден ВСЕМУ прогону**: его может поднять **любой** последующий шаг
  (через `recall('artifacts')`) и на нём же судит **критик** этого шага. Это «глобальная
  переменная» прогона — пиши сюда то, что важно вообще, а не только следующему шагу. Артефакт
  **по желанию**: шаг сам решает, что достаточно важно, чтобы стать артефактом (но см. правило
  ниже про шаги с критиком). Хранятся по шагам весь прогон, видны в `claw log`.
- **Handoff — канал «только следующему шагу».** **Селективная** эстафета: не весь контекст, а
  «на что обратить внимание дальше». В отличие от артефакта handoff **виден ровно одному
  следующему шагу** и дальше не живёт. В конце шага движок **осознанно просит модель**
  сформировать handoff (что сделал + находки/гочи для следующего), **продолжая ту же
  turn-loop-историю шага** (модель ещё помнит свои тул-вызовы, что читала/меняла), а не холодную
  выжимку. Формируется **лениво** (только если следующий шаг реально зовёт `ai()`), пишется в
  журнал и автоматически подставляется в системный промпт следующего шага. **Durable:** в тот
  же момент сохраняется в стор с привязкой к шагу-источнику, так что при resume в новом процессе
  поднимается из БД без повторного запроса к модели (детали — в «Состояние и durable resume»).
- **Param — канал «чёткое значение для КОДА».** `$this->setParam('name', $value)` фиксирует конкретную
  величину (путь, число, id, флаг стратегии), а любой следующий шаг читает её `$this->param('name')` и
  использует **в коде детерминированно** — в отличие от artifact (контент для модели) и handoff (проза
  для модели). **Durable:** едет в снапшоте под зарезервированным ключом, переживает resume (восстанавливается
  в конструкторе). **Полностью опционален:** большинство шагов так ничего не передают, и это нормально —
  валидатор параметров не требует; тянись к нему, только когда PHP позднего шага реально нужна величина,
  вычисленная ранним. (Это НЕ возврат «старой модели полей»: это явный durable API с именем, а не неявная
  плумбинг-переменная.)

**Разница, которую нельзя путать:** handoff — приватная записка СЛЕДУЮЩЕМУ шагу (узкий, временный,
последовательный баton); artifact — публичный результат, видимый ВСЕМ шагам и критику (широкий,
живёт весь прогон). handoff — для «передай дальше вот это», artifact — для «это результат, пусть
будет доступен всем (и судье)».

**Правило шага с критиком.** Если у шага есть `#[Step(critic: …)]`, он **обязан** завершиться
хотя бы одним из каналов — **artifact и/или handoff** — потому что именно их судит критик. Шаг
с критиком, не оставивший ни артефакта, ни handoff'а, ничего не произвёл — это ошибка генерации,
а не «нечего ревьюить». (У шага без критика канал по желанию.)

- **`recall(what, name?)`** — тул, поднимает из журнала контекст по запросу: бриф задачи,
  карту шагов, историю шага/тула, **артефакты** (так последующий шаг и читает глобальный канал).
  Решает генератор, что подтянуть.
- **`done(summary)`** — тул: модель объявляет задачу решённой и **завершает workflow досрочно**
  (бросает `WorkflowFinished`, `run()` ловит). Для простой задачи, которой не нужны все шаги.

## Наблюдаемость (`Claw\Trace`)

Журнал (`Claw\Journal`) был скелетом без боевой реализации — **удалён** и заменён
нейтральным нижним слоем `Claw\Trace` (на него опираются Agent + Workflow + bin, что
заодно убрало течь Agent→Workflow). `Tracer` — типизированный фасад
(`enterWorkflow/enterStep/enterAi/enterTurn/exit`, `prompt/reply/toolCall/toolResult/log`):
держит стек родителей и id, разводит каждую запись по списку **синков** (падение синка не
ломает прогон). Синки: `TraceStore` (таблица `trace` в БД проекта), `ConsoleTraceSink`
(живой отступной вывод в stderr), `ArrayTraceSink` (память/тесты). В `reply` лежит расход
токенов — **trace заодно работает cost-ledger'ом**. Читалка истории — `TraceReader` +
`claw log [runId]` (только чтение, без ключа): печатает дерево прогона
`workflow → step → ai(role+model) → turn → reply[tok] / tool / tool-result`. `-v` поднимает
порог детализации (полные промпты/ответы), `-q` опускает до вех.

**Раскраска.** И живой вывод, и `claw log` тинтуют каждую строку **по типу события** — через
единственную палитру `TraceFormat::paint` (одно место форматирования, чтобы live и история
красились одинаково): структура (`workflow`/`step`), слова модели (`prompt`/`reply`), машинерия
(`tool`/`turn`) и подсвеченный `handoff` читаются с одного взгляда. Цвет включается
**автоматически** только если поток — настоящий терминал и не задан `NO_COLOR`; в пайпах, файлах
и выводе `recall` остаётся чистый текст.

## Модель исполнения

- Шаги идут **последовательно** в `run()` — это обычный PHP. Циклы/ветвления — это
  `if`/`while`; цельную переиспользуемую повторяемую процедуру выражают **под-workflow**,
  а не «магией» цикла.
- `ai()` стоит на `DefaultTurnLoop` — ReAct-петле. Headless по умолчанию, но с `ask`-каналом
  становится интерактивной (маркер `[question]`); ограничена **turn-бюджетом** + мягким **капом
  в 50 turn'ов** (пауза-вопрос «continue?», в headless — стоп, чтобы не убегать). `ai()` ещё и
  умеет **продолжить** переданную историю — на этом стоит формирование handoff в контексте шага.
  Отмена просто всплывает исключением через structured concurrency.
- **Бюджеты (`Claw\Agent\Budget`).** Меряют токены (начисляются по ходу) и время (инжектируемые
  часы), parent-цепочка: turn-бюджет — ребёнок тотального (`spend` пробрасывается вверх,
  `isExhausted()` смотрит себя и предков, `0` = без лимита). **Тотальный** (`EnvKey::Budget`):
  `ai()`/`step()` его проверяют; исчерпан → стоп или pause-`ask` по `BudgetPolicy` (человек вводит
  прибавку `+N` → `raise()` → продолжаем). **Turn** (`TurnTokenLimit`/`TurnTimeLimit`): мягко
  закрывает один обмен в лупе. Лимиты из `.env` (`CLAW_BUDGET_*`, `CLAW_TURN_*`,
  `CLAW_BUDGET_POLICY`). Бюджет лежит в `Claw\Agent`, чтобы луп его видел без течи Agent→Workflow.
- **План:** параллельные задачи внутри шага (`spawn`/`await`, барьер на обязательных).

## Создание и хранение workflow

- **`DefineWorkflowTool`** (`define_workflow`): агент отдаёт PHP-класс, наследник
  `WorkflowAbstract`; он валидируется и сохраняется. Инструмент `Dangerous` — гейтится
  permission-слоем.
- **`WorkflowValidator`**: статическая проверка кода (запрет `eval`/`include`/backtick/
  динамических `$fn()`/опасных builtin; те же имена как методы разрешены). Плюс требует, чтобы
  каждый `#[Step]`-метод был **`protected`** — `public`/`private` отклоняются с понятной ошибкой
  (заставляем генератор писать шаги правильно, без костылей в движке).
- **`WorkflowStore`**: `write`/`classFor` — сохранение в сессионную или общую (`Common`)
  область.
- Человек одобряет корневой workflow и продвижение в `Common`; запуск инициирует человек.

## Безопасность

1. **Валидатор кода** перед загрузкой класса.
2. **Единственная дверь:** воркфлоу трогает мир только через поверхность
   `WorkflowAbstract` (`ai`/`tool`/`param`/…).
3. **Палитра = наименьшие привилегии:** `ai()` сужает реестр scope до `only($tools)` —
   и видимость, и исполнение ограничены одним набором.
4. **Permission-слой** (`risk`: confirm/deny, денлист) гейтит конкретный вызов — общий и
   для шагов, и для прямых `tool()`. В автономном прогоне пока allow-all; реальная
   политика — с run-path.
5. **Control flow — это код, не модель.** Порядок/ветвления решает PHP в `run()`/телах
   шагов; вывод модели — это данные. Инъекция в данных может максимум испортить
   результат шага, но не перехватить поток.
6. **Человек — корень доверия.** Корневой workflow и продвижение в `Common` утверждает
   человек; производный workflow не шире прав родителя (анти-эскалация).

## Память (три памяти, не путать)

1. **Рабочая** — состояние прогона (поля + снапшот в сторе). Эфемерна для одного
   прогона, восстановима при resume.
2. **Процедурная** — сами workflow как код («как мы это делаем»).
3. **Декларативная** — база знаний (`Claw\Knowledge`: `KnowledgeBaseInterface`,
   `Article`, `Tag`, `Provenance` — **скелет**). **План:** хранение как
   Obsidian-совместимые MD в репозитории (frontmatter, `[[wikilinks]]`, папки = scope),
   затем `search()` через `sqlite-vec` + провайдер эмбеддингов; KB как Tool.

## Что реализовано / что в планах

**Реализовано:** `WorkflowInterface` + `WorkflowAbstract` (хелпер), атрибут `#[Step]`,
`Environment`/`EnvKey`, `WorkflowStateStore` + `SqliteStateStore` (боевой снапшот) +
`InMemoryStateStore` (тесты), `Registry` с палитрой (`only`/`specs`), `ChainExecutor` +
middleware, `DefaultTurnLoop`, наблюдаемость `Claw\Trace` (+ `claw log`), `Claw\Project`
(`Project`/`Issue`/`ProjectStore` с ledger прогонов), `define_workflow` +
`WorkflowValidator` + `WorkflowStore`, пример `ReviewFileWorkflow`.

**Run-path построен** (`Claw\Cli\WorkflowMode`): `claw -c / -i / run / log` —
композиционный корень строит `Environment` с дефолтами проекта и гонит `WorkflowAbstract`.
Дефолт — `GenerateIssueWorkflow` (мета-workflow: **understand → assess → draft → review → save**:
понять задачу → оценить сложность и выбрать тир модели для солвера → сгенерировать солвер →
ревью супервизором → сохранить через `define_workflow`; затем апрув человека → прогон в реальной
папке проекта). Само мышление генерации идёт на **smart-тире**. Сгенерированный солвер следует
каноничному 7-шаговому рецепту (validate → design → SOLID-review+гейт → implement → test&accept →
changelog → deliver). На успешном финише прогон → `done`, issue → `Done`. Роли проброшены;
durable resume — через `ProjectStore::resumableRun`.

**Построено (эта сессия):** инверсия палитры (по умолчанию ВСЕ тулы), tool-briefing в системный
промпт, локальные `#[Tool]`-методы; критик переписан — **обычный AI со всеми тулами**, правила
`criticRules()`, роль `criticRole()`, судит каналы вывода шага (artifact/handoff); тиры моделей (`*-smart`);
**артефакты** (`artifact()`); тул **`recall`** (контекст из журнала); **мягкие капы циклов**
(`maxRounds` + эскалация, turn-cap) поверх бюджета; тул **`done`** (досрочный чистый финиш);
`tool()` больше **не бросает** (ошибка → строкой модели); шаги обязаны быть **`protected`**
(валидатор); **handoff** — селективная эстафета, осознанно формируемая моделью в контексте шага.

**Построено (последняя сессия):** **handoff стал durable** — формируется по-прежнему лениво, но в
тот же момент пишется в стор с привязкой к шагу-источнику (`saveHandoff`/`loadHandoff`,
`workflow_handoff` в SQLite); при resume в новом процессе он поднимается из БД **без повторного
запроса к модели**, а handoff от уже отработавшего перехода отбраковывается как устаревший. **Trace
раскрашивается по типу события** (единая палитра `TraceFormat::paint`) — одинаково в живом выводе и в
`claw log`, авто-включение по TTY/`NO_COLOR`.

**В планах** (приоритезировано разделом «Где мы относительно исследований»):

- **Внешний приёмочный гейт** — на `claw run` опереть статус `done` на реальный прогон тестов
  (`composer qa`), а не на самооценку; гард от преждевременного «готово» (#2/#7).
- [ ] **Разумный дефолтный бюджет токенов на run** (сейчас `CLAW_BUDGET_TOKENS=0` = безлимит). Даже
  с предохранителями (circuit-breaker на залипший тул, мягкие капы циклов) автономный прогон без
  потолка — риск; поставить вменяемый дефолт в `.env.example`, чтобы любой будущий залип сам себя
  остановил. (Бюджет как ИНСТРУМЕНТ ТЕСТА — ограничить run и смотреть «дошёл/не дошёл» — НЕ годится:
  кап режет легитимный прогон и даёт ложный сигнал; это бэкстоп безопасности, не критерий успеха.)
- **Permission `Policy`** для автономного `bash` (сейчас allow-all): денлист → AI-оценка риска.
- **Компакция контекста** на длинных прогонах; **эпизодическая память** (рефлексия между прогонами).
- **База знаний** (Obsidian-MD + `sqlite-vec`); **параллельные задачи** в шаге.
- **Валидатор-проверка handoff/тулов** и прочая шлифовка генерации.

## Где мы относительно исследований по Loop-агентам

Карта нашей петли на фоне литературы. Полный обзор с источниками (ReAct, Reflexion,
Self-Refine, AlphaCodium, SWE-agent, Anthropic *Building Effective Agents* / multi-agent,
DeepMind о само-коррекции, Context Rot, OWASP LLM06 и др.) —
[`agentic-loops-survey.md`](agentic-loops-survey.md).

По оси «**workflow** vs **agent**» (Anthropic, *Building Effective Agents*, дек. 2024) мы
сознательно на стороне **workflow**: поток управления держит КОД (`run()` + `#[Step]`), а
модель заполняет локальные решения. Ставка верная — и Anthropic, и Cognition сходятся, что
для кода непрерывный единый контекст и детерминированный костяк бьют автономный
много-агентный рой.

**Где мы сильны:**

- **Workflow-не-agent.** Управление — код, вывод модели — данные: инъекция в данных портит
  максимум результат шага, не поток.
- **Durable resume.** Снапшот `{state, done}` + сохранённый handoff + ledger прогонов +
  до-исполнение хвоста — это паттерн LangGraph-checkpointer / Temporal.
- **Процедурная память как код.** Workflow'ы — растущая библиотека исполняемых навыков:
  прямой аналог skill-library из Voyager.
- **Валидатор + апрув человека + `protected`-шаги** — сильно по OWASP LLM06 (excessive
  agency); палитра по умолчанию полная, но всё за «единственной дверью» и под политикой.
- **Trace как cost-ledger** — токены в `reply` дают готовый субстрат для бюджетов.
- **Петля ограничена** — бюджеты (токены+время) + мягкие капы (`maxRounds` критика, turn-cap) с
  эскалацией: «bound every loop».
- **Критик + супервизор + эскалация к человеку** — proposer/disposer; критик — AI **с тулами**,
  реально верифицирует (а не LLM-judge по тексту); на крах кода — авто-починка (`SuperviseWorkflow`).
- **Контекст-инженерия** — изоляция шагов + селективная эстафета (handoff) + `recall`/артефакты
  против Context Rot; досрочный `done` против лишних шагов.

**Что мы упустили — пробелы.** Подробный разбор — в [`workflow-gaps.md`](workflow-gaps.md).
**Закрыто:** (1) предел петли — бюджеты + мягкие капы циклов; (3) цикл починки —
`SuperviseWorkflow`; критик теперь **верифицирует тулами** (открывает файлы, гоняет `php -l`/
тесты), а не судит текст. **Остаётся:** (2/7) внешний гейт на тестах и **гард преждевременного
`done`** (сейчас `done` — на доверии модели); (4) компакция контекста; (5) эпизодическая память;
(6) права автономного `bash`.
