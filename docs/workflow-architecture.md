# Архитектура Workflow

Дизайн-документ: модель «умных workflow» для php-claw — идея, как устроен код
**сегодня**, и что ещё впереди. По тексту помечено, что **реализовано**, а что **в
планах**. Это спека, а не туториал.

## Идея

Агент решает каждую задачу заново, и его опыт исчезает вместе с окном контекста.
Workflow лечит это, превращая модель из **интерпретатора** в **компилятор плюс
оркестратор**: человек описывает процесс словами, агент собирает из готовых блоков
исполняемый PHP-класс, и дальше этот класс прогоняется как код. Структура процесса
детерминирована и восстановима, а отдельные шаги внутри могут быть агентными (вызовы
LLM) там, где нужна гибкость.

Отличие от «скилов»: скил перечитывается и толкуется моделью при каждом запуске
(дорого, недетерминированно). Workflow пишется один раз, исполняется предсказуемо, его
можно прочитать, проверить, сохранить и переиспользовать.

## Что такое Workflow (текущая модель)

**Workflow — это PHP-класс с состоянием в собственных полях.** Шаги — это **методы**,
помеченные атрибутом `#[Step]`. Базовый `WorkflowAbstract` — **тонкий хелпер, а не
движок**: он ничего «за шаг» не исполняет, он лишь делает тело шага короче и durable.

```php
interface WorkflowInterface
{
    public function name(): string;
    public function run(): void;   // точка входа; результат — состояние, что осело в полях
}
```

- **Состояние** — поля класса. Между шагами данные передаются через них (или через
  обычные переменные внутри `run()`), а не через возвраты.
- **Шаг** — метод с `#[Step]`. Тело пишет автор (человек или AI) руками: собрать промт,
  позвать `ai()`, позвать `tool()`, записать результат в поле.
- **`run()`** — просто точка входа. По умолчанию база гонит `#[Step]`-методы в порядке
  объявления; автор может **переопределить** `run()` и оркестрировать руками обычным
  PHP (`if`/`while`, под-workflow).

Пример — `src/Workflow/Example/ReviewFileWorkflow.php`:

```php
final class ReviewFileWorkflow extends WorkflowAbstract
{
    private string $source = '';
    private string $issues = '';
    private string $proposal = '';

    public function name(): string { return 'review-file'; }

    #[Step]
    public function read(): void
    {
        $this->source = $this->tool('read_file', ['path' => (string) $this->param('path')]);
    }

    #[Step]
    public function findIssues(): void
    {
        $this->issues = $this->ai("List the problems in this file:\n\n" . $this->source);
    }

    #[Step]
    public function propose(): void
    {
        $this->proposal = $this->ai("Propose concrete fixes for:\n\n" . $this->issues);
        // критик — это подшаг: ещё один вызов ai(), результат которого автор разбирает кодом
        $verdict = $this->ai("Reply only 'ok' or 'weak':\n\n" . $this->proposal);
        if (str_contains(strtolower($verdict), 'weak')) {
            $this->proposal = $this->ai("Make it stronger:\n\n" . $this->proposal);
        }
    }
}
```

## Параметры (в этом и есть супер-сила)

Workflow **параметризирован**: принимает входные параметры и потому описывает не одну
задачу, а целый их класс. Workflow «прочитай и отревьюь файл» бесполезен без ответа
«какой файл» — и это **параметр**. Один и тот же класс работает для любого файла:
достаточно передать параметр при запуске. Связка **Workflow + параметры** и есть его
мощь: класс — это шаблон процесса, параметры — конкретика.

Заполнять параметры может **человек или агент**: «отревьюь src/Foo.php» агент
превращает в `path = src/Foo.php`. Технически шаг читает их через `$this->param('path')`;
параметры приходят в конструктор инстанса.

## База-хелпер: поверхность `WorkflowAbstract`

Это и есть «единственная дверь» — генерируемый подкласс трогает мир только через эти
методы:

- **`ai(string $prompt, array $tools = []): string`** — один обмен с моделью; турн-луп
  внутри (ReAct: round-trip'ы с инструментами) — внутренняя деталь. `$tools` — палитра
  наименьших привилегий: модель **видит и может запустить** только их.
- **`tool(string $name, array $params): string`** — один вызов инструмента через
  executor прогона; бросает при ошибке инструмента.
- **`param(string $name): mixed`** — вход прогона.
- **`step(string $name): void`** — выполнить `#[Step]`-метод, если он ещё не сделан, и
  снять снапшот состояния (ниже). По умолчанию `run()` зовёт его на каждый шаг; в своём
  `run()` автор зовёт его в нужном порядке/по условию.
- **`find()/set(EnvKey|string)`** — читать/локально переопределить окружение прогона
  (обычно из `init()`).
- **`log(action, message, context)`** — записать в журнал событие уровня задачи.
- **`init()`** — хук: настроить scope прогона до первого шага.

## Состояние и durable resume (снапшот)

Прогон **durable по СНАПШОТУ** (не по replay результатов):

- после каждого шага база сохраняет в `WorkflowStateStore` пару `{state, done}` по
  `runId` — где `state` это поля воркфлоу, а `done` это имена выполненных шагов;
- в конструкторе снапшот загружается: `state` **восстанавливается на поля** (рефлексией
  по собственным свойствам подкласса), `done` — в список сделанных;
- `step(name)` **пропускает** шаг, уже попавший в `done`. Поэтому пропущенный шаг
  ничего не теряет — его эффект уже в восстановленном состоянии.

**Реализовано:** `InMemoryStateStore` (в памяти; не переживает рестарт процесса).
**План:** durable-стор на SQLite + реестр прогонов и recovery при старте.

Контракт стора: `save(runId, state, done)` / `load(runId) -> {state, done}` /
`nextId()` (монотонный id для leaf-вызовов — стор владеет идентичностью, воркфлоу id не
выдумывает).

## Environment (окружение прогона)

`Environment` — scoped `key→value` с ссылкой на родителя. `find()` ищет в этом scope,
затем поднимается к родителю — так цепочка **project → issue → workflow →
под-workflow** наследует значения, а ребёнок переопределяет только нужное. `EnvKey` —
каталог известных ключей: `Worker`, `Registry`, `ModelId`, `SystemPrompt`, `MaxHistory`,
`Store`, `Journal`. Типобезопасные finders над «mixed»-мешком; `executor()` собирается
из реестра текущего scope.

## Инструменты и палитра (наименьшие привилегии)

`Registry` — каталог инструментов. `ai($prompt, $tools)` создаёт дочерний scope с
`registry.only($tools)` — суженным реестром. Из него берутся **и** спеки (что видит
модель), **и** резолв исполнения (`executor()` бьёт по реестру scope). Поэтому
инструмент **вне палитры** не рекламируется и не запускается — видимость и исполнение
это один набор.

Исполнение идёт через `ChainExecutor` с middleware (audit / permission / timeout).
**Сейчас** executor воркфлоу собран без permission-middleware (автономный прогон =
фактически allow-all); реальная `Policy` (денлист, позже — AI-оценка риска) приедет с
run-path (ниже).

## Критик и супервизор — это подшаги

В `step()`/`run()` **нет** зашитого критика, супервизора, политики повторов. Критик —
это **подшаг**: ещё один вызов `ai()` внутри тела шага, который судит результат, а автор
разбирает вердикт обычным PHP (см. `propose()` в примере). Так же и супервизор
(разблокировать застрявший шаг). Ничего из этого не встроено в базу.

## Журнал

`Claw\Journal`: `JournalInterface`, `JournalEntry`, `JournalScope`
(Project / Issue / Workflow / Step / Task). `step()` пишет запись уровня `Step`,
`log()` — уровня `Task`; обе проставляют lineage (project / issue / workflow). Аудит
вызовов инструментов вливается в тот же журнал через `AuditMiddleware` (единый funnel).

## Модель исполнения

- Шаги идут **последовательно** в `run()` — это обычный PHP. Циклы/ветвления — это
  `if`/`while`; цельную переиспользуемую повторяемую процедуру выражают **под-workflow**,
  а не «магией» цикла.
- `ai()` стоит на `DefaultTurnLoop` — headless ReAct-петле (без UI/отмены/сообщений
  человеку; отмена просто всплывает исключением через structured concurrency TrueAsync).
- **План:** параллельные задачи внутри шага (`spawn`/`await`, барьер на обязательных).

## Создание и хранение workflow

- **`DefineWorkflowTool`** (`define_workflow`): агент отдаёт PHP-класс, наследник
  `WorkflowAbstract`; он валидируется и сохраняется. Инструмент `Dangerous` — гейтится
  permission-слоем.
- **`WorkflowValidator`**: статическая проверка кода (запрет `eval`/`include`/backtick/
  динамических `$fn()`/опасных builtin; те же имена как методы разрешены).
- **`WorkflowStore`**: `write`/`classFor` — сохранение в сессионную или общую (`Common`)
  область.
- Человек одобряет корневой workflow и продвижение в `Common`; запуск инициирует человек.

## Безопасность

1. **Валидатор кода** перед загрузкой класса.
2. **Единственная дверь:** воркфлоу трогает мир только через поверхность
   `WorkflowAbstract` (`ai`/`tool`/`param`/…).
3. **Палитра = наименьшие привилегии:** `ai()` сужает реестр scope до `only($tools)` —
   и видимость, и исполнение ограничены одним набором.
4. **Permission-слой** (`risk`: confirm/deny, денлист) гейтит конкретный вызов — общий и
   для шагов, и для прямых `tool()`. В автономном прогоне пока allow-all; реальная
   политика — с run-path.
5. **Control flow — это код, не модель.** Порядок/ветвления решает PHP в `run()`/телах
   шагов; вывод модели — это данные. Инъекция в данных может максимум испортить
   результат шага, но не перехватить поток.
6. **Человек — корень доверия.** Корневой workflow и продвижение в `Common` утверждает
   человек; производный workflow не шире прав родителя (анти-эскалация).

## Память (три памяти, не путать)

1. **Рабочая** — состояние прогона (поля + снапшот в сторе). Эфемерна для одного
   прогона, восстановима при resume.
2. **Процедурная** — сами workflow как код («как мы это делаем»).
3. **Декларативная** — база знаний (`Claw\Knowledge`: `KnowledgeBaseInterface`,
   `Article`, `Tag`, `Provenance` — **скелет**). **План:** хранение как
   Obsidian-совместимые MD в репозитории (frontmatter, `[[wikilinks]]`, папки = scope),
   затем `search()` через `sqlite-vec` + провайдер эмбеддингов; KB как Tool.

## Что реализовано / что в планах

**Реализовано:** `WorkflowInterface` + `WorkflowAbstract` (хелпер), атрибут `#[Step]`,
`Environment`/`EnvKey`, `WorkflowStateStore` + `InMemoryStateStore` (снапшот),
`Registry` с палитрой (`only`/`specs`), `ChainExecutor` + middleware,
`DefaultTurnLoop`, `Claw\Journal`, `Claw\Project` (`Project`/`Issue`),
`define_workflow` + `WorkflowValidator` + `WorkflowStore`, пример `ReviewFileWorkflow`.

**В планах** (см. `workflow-roadmap.md`):

- **Run-path / composition root** — главный пробел: пока **ничто не запускает** новую
  модель в проде. Нужен корень, что строит `Environment` с дефолтами проекта
  (worker / registry / store / journal) и путь, который инстанцирует сохранённый класс и
  зовёт `run()`. Туда же — permission `Policy` для автономного прогона.
- **Durable SQLite-стор** + реестр прогонов и recovery при старте.
- **Человек в петле** (`waiting_human`: пауза, карточка, мягкий таймаут, очередь,
  маршрутизация ответа).
- **База знаний** (Obsidian-MD + `sqlite-vec`).
- **Параллельные задачи** в шаге; **бюджеты**; **мутация** (workflow создаёт workflow).
