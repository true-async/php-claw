# Архитектура Workflow

Дизайн-документ. Сводит воедино модель умных workflow для php-claw: сущности,
компоненты, модель исполнения, память, безопасность и жизненный цикл. Это спека
для проектирования и реализации, а не туториал.

## Идея

Агент решает каждую задачу заново, и его опыт исчезает вместе с окном контекста.
Workflow лечит это, превращая модель из **интерпретатора** в **компилятор плюс
оркестратор**: человек описывает процесс словами, агент собирает из готовых блоков
исполняемый PHP-класс, и дальше этот класс прогоняется как код. Структура процесса
детерминирована и восстановима, а отдельные шаги внутри могут быть агентными
(вызовы LLM) там, где нужна гибкость.

Ключевое отличие от «скилов»: скил перечитывается и толкуется моделью при каждом
запуске (дорого, недетерминированно). Workflow компилируется один раз, исполняется
предсказуемо, его можно прочитать, проверить, сохранить и переиспользовать.

## Ключевые принципы

1. **Управление как данные.** Решение «продолжать / звать человека / повторить /
   стоп» это не свободное рассуждение модели, а отдельное поле шага с оценкой под
   ним. Мягкое суждение превращается в проверяемый сигнал.
2. **Способности, а не свобода.** Доступ к инструментам, агентам и записи в память
   выдаётся явно (через единственную дверь и только то, что прописано в workflow).
3. **Всё состояние в контексте.** Ничего важного не живёт в локальных переменных
   между шагами, поэтому workflow замораживается и размораживается через журнал.
4. **Человек это корень доверия.** Расширение прав (корневой workflow, общая папка)
   требует человека; использование уже выданных прав не требует.

## Сущности

### Workflow

Упорядоченная последовательность шагов `1..N`, оформленная как PHP-класс. Тонкий
интерфейс:

```php
interface WorkflowInterface
{
    public function name(): string;
    public function description(): string;
    public function run(WorkflowContext $ctx): void;
}
```

Вся механика (порядок шагов, циклы, ветвление, бюджеты, политика переходов) живёт
внутри `run()` как императивный код, опирающийся на контекст. Возвращать нечего:
результат это артефакты, осевшие в дереве контекстов.

### Шаг (Step)

Единица процесса и сущность с пятью свойствами:

1. **описание** — что сделать;
2. **ход** — процесс выполнения (история turnLoop);
3. **артефакты** — результат;
4. **оценка** — суждение критика о результате;
5. **вывод** — исход: идти дальше / прервать workflow / ждать человека / повторить.

Шаги идут **строго последовательно**, всегда. Это даёт дешёвый resume и
детерминированный порядок. Шаг это один или несколько turnLoop; если шаг это
вложенный workflow, он становится поддеревом.

### Задача (Task)

Единица работы **внутри** шага. Задачи могут идти **параллельно**. Задача это одно
из трёх:

- промт агенту (вызов LLM),
- вызов Tool,
- вызов другого workflow (под-workflow).

Задача бывает **обязательной** или **необязательной**. Обязательные образуют барьер
завершения шага; необязательные собираются best-effort, их провал или таймаут шаг
не срывает (это деградация, не срыв, и критик это учитывает в оценке).

### Контекст шага

У каждого шага два контекста:

- **пред-контекст** — вход, с которым шаг стартует (инструкция плюс артефакты
  предшественников как сообщения). Фиксирован на момент старта. Это и есть решение
  «потока данных» между шагами: не слепое наследование родителя и не голый старт, а
  явно собранный вход. Его неизменность даёт детерминизм переходов.
- **рабочий контекст** — пред-контекст плюс всё, что нарастил turnLoop. Непрерывно
  сохраняется, поэтому доступен при возобновлении даже посреди шага.

По сути контекст это история turn (`list<Message>`: user / assistant / tool_use /
tool_result). Новизны в формате нет, новизна в том, что историй много (по одной на
узел дерева), а не одна плоская.

### Дерево контекстов и карточка шага

Контексты образуют **дерево**: у каждого шага свой изолированный контекст-ветка,
вложенный workflow это поддерево. Агент по желанию поднимается к родителю или
заглядывает вбок.

Чтобы навигация не переполняла окно, у узла есть **карточка** (описание, оценка,
вывод): лёгкая выжимка для обзора. Важно: карточка это **не** усечение хранилища.
Хранится всё и всегда полностью (сырьё для отладки, аналитики и вывода будущих
workflow из траекторий). Карточка это проекция поверх полного архива; полную историю
шага агент разворачивает по запросу.

### Агенты

Шаг исполняет агент. Каких именно агентов использовать, может решать **другой агент**
(маршрутизатор), выбирая по контексту. Агенты переиспользуемы как **Tool-агент**
(обёртка агента в инструмент) или **субагент**. Разные шаги могут использовать разных
агентов.

### Критик

Отдельный агент, оценивающий результат шага. Какой критик на каком шаге, описывается
в workflow или контексте; критики могут быть разными для разных шагов. Критик выдаёт
**не** жёсткий приказ, а **оценку** (например по шкале 0–5) и может посоветовать
обратиться к человеку. Решение (повтор / дальше / эскалация) принимает **код
workflow** по порогам и настройкам. То есть суждение мягкое и от LLM, а политика
переходов жёсткая и детерминированная.

### ToolSet

Набор инструментов, выдаваемый агенту. Наборы у разных агентов **разные**, и какой
ToolSet кому доступен, описывает workflow. Это даёт наименьшие привилегии (узкий урон
при ошибке/инъекции) и качество выбора (меньше шума в палитре). ToolSet это, по сути,
именованное подмножество `Registry`.

### Бюджет

Общее ограничение на прогон: токены, время, деньги. Является частью контекста и
вводится сразу. Нарезается как прописано в workflow: по умолчанию общий пул,
по требованию выделенные под-лимиты под-workflow. Исчерпание жёстко останавливает.

## Модель исполнения

- **workflow это корутина** (одна на прогон; шаги это участки её тела, не отдельные
  корутины);
- **задачи это корутины** (`spawn` внутри шага, параллельно);
- **под-workflow это корутина** (вложенная, родитель её `await`).

Следствия:

- **Граница шага это барьер.** Шаг не закрывается, пока не собраны все обязательные
  задачи. В этой точке рабочий контекст фиксируется целиком.
- **Отмена каскадит.** `/stop` отменяет workflow-корутину, structured concurrency
  TrueAsync гасит её детей (задачи и под-workflow). Тот же механизм, что уже обкатан
  на turnLoop.

## Память

Три разные памяти, не путать:

1. **Рабочая** — дерево контекстов. Эфемерна (один прогон), обход структурный.
2. **Процедурная** — сами workflow как код. «Как мы это делаем».
3. **Декларативная** — база знаний (KB). «Что нам известно»: факты и выводы прошлых
   прогонов; переживает прогоны, общая.

Навигация по дереву (рабочая память) **структурная** и детерминированная:
`parent()`, `step(n)`, `siblings()`. RAG (семантический поиск) уместен **только** над
базой знаний и нужен **позже**, когда она разрастётся. Запись в KB разрешена агенту
**только если это предписано в workflow**.

## Управление потоком

- Критик даёт **оценку** (скаляр) и опциональный совет.
- **Код workflow** читает оценку и по порогам/настройкам выбирает исход.
- Исходы: дальше / прервать всё / ждать человека / повторить.
- Повтор ограничен потолком (часть политики в коде); исчерпание потолка ведёт к
  эскалации человеку.
- Ветвление по данным выражается обычным `if`/`switch` в императивном `run()`.

## Durable execution и восстановление

- Всё нужное для продолжения лежит в контексте шага, ничего в локальных переменных.
- Рабочий контекст фиксируется **после каждого побочного действия** (после каждого
  `tool_result`), чтобы resume не повторил эффект.
- **Resume** это переисполнение `run()` с пропуском сделанных шагов (их артефакты
  берутся из журнала) до первого незавершённого; внутри шага пересобираются только
  незавершённые обязательные задачи.
- Адресация цикла включает **итерацию** (шаг N, проход K), иначе resume в середине
  цикла неоднозначен.
- Ветвление при replay опирается на **сохранённые** артефакты, не на свежий вызов,
  иначе недетерминированный агент уведёт ветку.

### Восстановление после краха

Система ведёт реестр workflow со статусом и указателем на текущий шаг (ложится на
SQLite). При старте процесса:

- **running** (упал во время работы) → возобновить с рабочего контекста;
- **waiting_human** → не возобновлять, восстановить ожидание;
- **done / aborted** → не трогать.

Защита от краш-цикла: если шаг падает детерминированно, после N попыток
восстановления его переводят в `waiting_human` (исчерпанное восстановление это просто
ещё один путь к выводу «звать человека»).

## Человек в петле (waiting_human)

- Ситуация, когда нужен человек: workflow приостанавливается и шлёт сообщение через
  `ConversationInterface` (Telegram/консоль уже готовы; для решений есть inline-кнопки
  из `confirm()`).
- Сообщение несёт **карточку шага** (что застряло и что нужно), а не голое «эй чувак».
- Ожидание **мягкое, с таймаутом**: не дождались за ~5 минут — повтор по настройке.
  Дедлайн хранится в состоянии шага (timestamp), а recovery-петля проверяет его при
  тике; это не живой таймер на корутине, иначе рестарт его потеряет.
- Новое, что нужно написать: **маршрутизация ответа** обратно в замороженный шаг.
  Входящее сообщение это не новый turn, а вход в рабочий контекст ожидающего шага.
  При нескольких ожиданиях нужна корреляция (через `callback_data` кнопки: «ответ
  шагу N»).

## Безопасность

Несколько слоёв:

1. **Валидатор кода.** Сгенерированный workflow проверяется токенайзером перед
   `require`: запрет `eval`, `include`, backtick, динамических `$fn()` и блок-листа
   опасных builtin (шелл/ФС/сеть/окружение). Те же имена как методы (`$ctx->...`)
   разрешены.
2. **Единственная дверь.** Workflow трогает мир только через `WorkflowContext`:
   вызвать агента/субагента, вызвать tool, пройтись по дереву, читать KB (и писать,
   если разрешено).
3. **Два слоя доступа.** ToolSet решает, что агент вообще **видит** (доступность);
   permission (risk: confirm/deny) решает, пропустить ли **конкретный** вызов.
4. **Природа данных против инъекций.** Контекст типизирован по источнику: результат
   `read_file` это «вывод чтения», а не реплика чата. Стоит нести и **уровень
   доверия** источника (локальный файл доверенне веб-страницы или чужой записи KB).
   Структурное разделение снижает инъекцию, но не убирает; страхует то, что критик
   возвращает **число**, а переходами рулит код, так что инъекция в данных может
   максимум подтолкнуть оценку, но не перехватить control flow.
5. **Цепочка доверия.** Человек это корень. Корневой workflow и продвижение в `Common`
   утверждает только человек. Workflow, созданный другим workflow, агент принимает
   сам, но при двух инвариантах: производный workflow **не шире** прав родителя
   (анти-эскалация); автономно созданный остаётся **session-scope** (в `Common` только
   через человека).
6. **Бюджеты и лимиты.** Потолок повторов, лимит шагов, токены, время. Без них циклы и
   повторы разоряют.

## Жизненный цикл создания workflow

1. Человек **описывает** процесс словами.
2. Агент уточняет требования в режиме **1 вопрос — 1 ответ** (фаза интервью).
3. Агент **генерирует** код workflow.
4. **Валидатор** проверяет код.
5. **Человек одобряет** корневой workflow (и любое продвижение в `Common`).
6. Запуск инициирует **человек**.

## Как это ложится на текущий код php-claw

Переиспользуется почти всё:

- `turnLoop` это исполнение шага; `Message`/история это контекст; `SessionStore`
  (SQLite) это persist и resume, реестр workflow и состояние шагов.
- `ConversationInterface` (+ Telegram, + inline-кнопки) это канал human-in-the-loop.
- `Registry` это палитра; ToolSet это её подмножество; `executor` middleware
  (permission/audit/timeout) это слой разрешений, общий и для шагов, и для задач.
- TrueAsync (`spawn`/`await`/cancel, structured concurrency) это модель исполнения и
  отмена.

Что нужно написать нового: понятия Шаг/Задача/Критик/Вывод как сущности, дерево
контекстов с карточками, движок durable resume и реестр восстановления, маршрутизация
ответа человека, бюджеты, статическая проверка графа workflow при создании.

## Открытые вопросы

- Точные критерии оценки (rubric) и как критик их получает.
- Версионирование workflow и дрейф/конфликты фактов в KB (см. «Library Learning
  Doesn't»: библиотека ценна находимостью, а не фактом существования).
- Статическая валидация **графа** workflow (достижимость шагов, висячие переходы,
  ссылки на несуществующий субагент/ToolSet/право KB).
- Точная корреляция ответов человека при нескольких одновременных ожиданиях.
- Идемпотентность побочных эффектов на границе «эффект случился, но не записан».
