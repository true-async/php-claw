Думал какой обучающий проект сделать для TrueAsync и в результате выбор остановился на аналоге OpenClaw. Почему именно он? Во-первых, потому что это новая область программирования (для меня в том числе). Обычно мы, PHP-программисты, делаем BackEnd, и редко, когда делаем консольные приложения. Во-вторых, потому что задача идеально подходит для демонстрации встроенной в ядро PHP асинхронности. И наконец, потому что это весело.

По поводу структуры статей. Они будут появляться по мере создания проекта и идти в том же порядке, в котором код проектируется. А это значит, что первым этапом будет не кодирование, а изучение решений конкурентов, самой задачи и подходов.

Какую задачу решает OpenClaw?

Большая языковая модель в браузерной вкладке умеет разговаривать, но не умеет ничего делать с вещами на компьютере. Она не запустит команду на сервере, не поправит файл, не сходит в базу и не напишет вам отчёт. Вы привязаны к чужому веб-интерфейсу и чужому облаку. OpenClaw — это персональный AI-агент, которого вы запускаете на своём железе и с которым общаетесь прямо из мессенджера, например из Telegram. Вы пишете ему как подрядчику, а он автономно выполняет реальные действия: гоняет команды в shell, читает и правит файлы, ходит в сеть, ставит задачи по расписанию и присылает результат обратно в чат. По сути, это Claude Code, у которого вместо терминала мессенджер.

Как выглядит работа приложения?

Приложение получает текст от пользователя и отдаёт его AI-агенту. В ответ агент может либо вернуть текст-ответ, либо потребовать запустить инструменты. Если AI вернул текст, просто пересылаем его пользователю, и на этом всё. Если AI запросил инструменты (например, выполнить команду в shell или прочитать файл), приложение выполняет их, возвращает результат обратно агенту, и тот продолжает работу. AI-агент снова может ответить либо текстом, либо новым запросом на инструменты. Так повторяется, пока не появится финальный ответ. Данный workflow называется агентный цикл (agentic loop).

Следуя из этого, определим два ключевых слоя приложения:

- Агент – код, связанный с работой агента
- Tool – инструмент, код, который даёт возможность агенту выполнять реальные действия
- Chat – слой, который обеспечивает взаимодействие между агентом и человеком

Агент может использовать Tool. Агент должен знать о существовании Tool, и о том какие возможности последний предоставляет. В свою очередь Tool не должен знать про агента.

Построим архитектуру приложения, опираясь на эти слои как основные.

```php
    // Главный цикл
    while (true) {
        // 1. Получаем текст от пользователя
        $text = $this->chat->receive();
        
        // 2. Сохраняем его в истории
        $this->history[] = $text;

        // 3. Цикл работы агента
        while (true) {
            
            // 4. Посылаем запрос агенту. Передаём ему всю историю!          
            $response = $this->agent->send(new AgentRequest(
                model: $this->model,
                messages: $this->history,
                system: $this->system,
                tools: $this->specs,
            ));

            $this->history[] = $response->content;

            // 5. Если агент прислал готовый ответ пользователю,
            // посылаем ответ и заканчиваем цикл агента.
            if ($response->isCompleted()) {
                $this->chat->send($response->text ?? '');
                break;
            }

            // 6. Запускаем инструменты, которые запросил агент, и сохраняем их результаты в истории.
            $results = [];
            foreach ($response->toolCalls as $call) {
                $results[] = $this->execute($call);
            }

            $this->history[] += $results;
        }               
    }
```

Обратите внимание, что агент получает всегда всю историю сообщений. Причина в том, что современный API агентов работает
как stateless, но при этом позволяет кешировать контекст и не учитывает одинаковые строки, которые были посланы недавно.
Но послать всю историю необходимо!

Кроме этого, мы так же посылаем агенту информацию об Инструментах (Tools), 
поэтому агент сразу же знает, какие инструменты может использовать.

Весь проект разобьём на три папки: `Agent`, `Tool` и `Chat`, в соответствии с выделенными слоями. 
В каждой папке будет интерфейс и его реализация, а также дополнительные DTO-структуры, которые позволят хранить
сообщения разного типа.

`ContentBlockInterface` нужен, чтобы выражать разные типы сообщений:
- Text
- ToolCall
- ToolResult

А контейнер Message будет связывать список ContentBlockInterface с конкретным отправителем (пользователь, агент, система)
и временем отправки.
